## 1. 对标拆解：怎么从一支对标片里"读出配方"

配方不是看出来的，是**扒出来的**。整条链路是：

```
选定对标片里"当配乐在用"的那一段
  → 转谱（拿调性/和弦/BPM/结构/旋律音序列）
  → 本地算音频侧指标（峰值位置/动态/声场/谱平坦度）
  → 把曲子映射到成片里的"实际使用窗口"
  → 把两边的六个量摆在一起 → 反推槽位配方
  → 按配方生成 → 把生成曲丢回转谱 → 看有没有落回目标（闭环）
```

### 1.1 取哪一段：要对齐的是"使用窗口"，不是整首曲子

**规则**：拆分对标的配乐，必须先拿到"这首曲子在成片里被用了 `[起, 止]`"这条映射
（来自配乐表：`track / offset / start / end`），所有"峰值位置、能量走势"都要在这个窗口内重算。

**为什么**：曲子自身的峰值位置与它在**成片里**听起来的峰值位置可以差很远。
示意：一段只取曲子的前 30 秒时，曲内 0.73 处的峰值根本不在这 30 秒里——
**不按使用窗口重算，就会把"峰值偏晚"读成"没问题"。**

**怎么验证**：对每个使用窗口量"窗内 argmax RMS 的相对位置"：

```
i* = argmax(RMS[i] for i in 使用窗口 [t0, t1))     # 逐秒 RMS
pos = (i* − t0) / (t1 − t0)                        # 0=窗口开头，1=窗口末尾
```

实测出现过一轮：开场曲既有的使用窗口里峰值落在 **0.37–0.59**，而配方要求开场类
**0.10–0.33** → 结论是"开场一直在往上爬，没有一上来就抓住人"。
到片尾（全片最后 12%）则是 0.886，落在要求的 0.75–0.96 内 ✓。

### 1.2 六个客观量（扒谱侧 + 音频侧）

| 量 | 从哪来 | 口径 |
|---|---|---|
| **调性** | 转谱产物 `key.lab` | 取末字段（如 `G:minor`） |
| **和弦** | `chord.lab` | 第 1 行常是表头；取前 8 行第 3 列即和弦序列 |
| **BPM** | `beat.lab` / 转谱任务字段 | 与曲内节拍一致 |
| **曲式** | `structure.lab` | 分段标签（前奏/主歌/高潮…），用来判断"有没有自然收束" |
| **音符密度** | `melody_instrumental.lab` 的**行数** | `notes / 全长秒 * 60` → 音/分 |
| **长音比例** | 同上，音符区间长度 | 时长 ≥ 1.0s 的音符占比；垫底类应该高 |

音频侧（本地 `ffmpeg` 解码 + `numpy`，不依赖模型）：

| 量 | 怎么算 | 用途 |
|---|---|---|
| **能量峰值位置** | 逐秒 RMS 的 argmax / 段长（0–1） | 判断"该早抓人还是该晚升华" |
| **动态范围** | 逐秒 RMS 的 P95 − P5（dB） | 太小的垫底曲会"平" |
| **声场宽度** | `RMS(side) / RMS(mid)` | 铺垫类可以窄一点 |
| **谱平坦度** | 每帧 FFT 的几何均值/算术均值，取中位 | 接近 1 = 像噪声/打击；小 = 有明确音高 |

**怎么验证密度算法没写错**：拿一首已知稀疏的垫底曲跑一遍——
实测三首曲子密度分别是 **228 / 126 / 36.7 音/分**，而配方要求垫底 **16–35**。
第一首的 228 是配方的 6 倍以上，这种量级差是"听得出来满"的直接原因，
如果算出来只有几十，先怀疑解码/时长口径。

### 1.3 三档槽位配方（对标得出的形态）

| 槽位 | 调性 | BPM | 和弦 | 目标密度 | 其它 |
|---|---|---|---|---|---|
| **开场冷蒙太奇** | 小调 | 60–65 | i–VI–VII | 20–50 音/分 | 窄音域长音；**能量峰值靠前（0.10–0.33）** |
| **铺垫 / 垫底** | 大调或小调 | 58–65 | **两个和弦就够** | **16–35 音/分** | "垫底不抢靠的是音符稀疏，不是把音量调小" |
| **高潮 → 收尾** | 小调，或大调 + bVI | 75–125 | i–VI–VII 或 I–V–IV | 34–100 音/分 | 弦乐长音；长音占比应高 |
| **片尾落版** | 大调 | 75–98 | I–V–IV–I | 49–61 音/分 | **峰值落在最后 4–10 秒（0.75–0.96）** |

**怎么验证**：三档里最容易被打满的是"铺垫垫底"——
生成出来的曲子天然往"满编"走，实测第一轮偏离配方 4–7 倍（126–228 音/分）。
**看到垫底曲密度 > 50 音/分，直接判不通过**，不要靠听感争论。

### 1.4 拆解对标片时必须先做的一个判断：形态是不是同一个物种

**规则**：先量对标片的**旁白覆盖率**（人声时长 / 全片时长）与**留白位置**，再决定"照搬什么"。

**为什么**：实测对标的 8 条代表作旁白覆盖率是 **98.5%–100%**（全程有人说话，
留白只出现在开场冷蒙太奇和高潮/延时段）；而当时的 5 分钟版是**纯音乐无旁白**，
属于"预告片/精华片"，**不是同一个物种**——直接照搬镜长、结构会错位。
结论是：叙事版必须有旁白，纯音乐版留作预告与分发，**两版分开定标准**。

**怎么验证**：ASR 逐段转写，按"有人声的秒数"求和算覆盖率；把留白段标在时间轴上
（应该只有开场与高潮两处）。

### 1.5 从对标片拆出的可执行剪辑规则（都被数据支持）

这些规则来自"逐镜头拆解 + ASR 听译 + 场景检测分镜表 + 开场 90 秒密采样"，与配乐同源：

1. **不是"3 秒一切"**：对标片里 **>5s 的镜头占 63.1%**，且"没有 1 秒以下的碎镜"；
   平均镜长落在 **5.6–10.2s** 都算正常。快切只放**开场、换地形、片尾**三处。
   *为什么*：为了"高级感"硬切碎会把沉浸感切没，而且对标的实测节奏并不快。
   *怎么验证*：算正文镜长中位数与 "≥8s 的镜数"（见 §6 验收表），别只看平均。
2. **口播 / 独白时绝不切画面**：对标片有单镜 106s、一镜到底 191.6s 的实例；
   **低谷用最长镜头让观众一起熬**（"低谷不剪，高峰才剪"）。
   *怎么验证*：把"有旁白"的镜头单独列出来，检查其画内切点数应为 0。
3. **旁白语速按段落类型分档**：行程交代类最快、爬升类中档、**到达类最慢**。
   实测口径：行程交代 **219 字/分**、爬升 **75 字/分**、到达 **34 字/分**；
   补录语速 120–140 字/分、每段 60–150 字。
   *怎么验证*：按段落分别统计字节数/秒数；到达段超过 ~50 字/分就是没压下来。
4. **数据浮层有节奏**：对标片约**每 5–8 分钟出现 1 个数据浮层**；全片标题条只 1 处。
   *怎么验证*：数浮层个数 / 片长。
5. **对标片是长片**（实测 19–27 分钟，冷开场 30–90s ≈ 全片 **2%–4%**）。
   **不要直接套绝对秒数**：先按比例算（5 分钟片 → 6–12s），再判断"这点时间够不够装
   标题 + 数字"；实测 81s 太慢、30s 仍偏慢、**20s 是三件事都能做完的最短长度**。
6. **能力缺口的替代清单**（对标片有、你没有时，用"结构等价的镜头"补，而不是硬凑）：
   航拍大全景 → 前景框景（树枝/经幡/门框/帐篷口）+ 4K→1080 裁切出 2× 伪长焦 + 人极小比例镜；
   固定机位延时 → 静止空镜放慢 + 缓推（并列入下次必拍）；
   对镜口播 → 后期旁白 + 花字 + 拟声；
   地图/数据动画 → 用轨迹点算出的里程/爬升/海拔剖面做成数据卡。
   *怎么验证*：逐条填入"他们必拍 / 我的库存 / 处置"，**库存为 0 的行必须有替代方案**，
   否则它就是下一个缺件。
7. **素材重估**：被判为"低价值"的一类镜头（如低头看路的贴地特写）可能正是对标
   "每 40 秒一个障碍"的节奏镜头——**换一个结构口径，同一批素材的评分会翻转**。

> ⚠️ "花字越多越掉高级感""某些档位必须用""撤旁白≠放慢"这类审美/风格结论，
> 在本次取材的源码与实测记录里**找不到可复算的证据**，见 §5 第 4 条，不要当判据用。

## 2. 把配方落到成片：槽位表 + 余量 + 接缝

### 2.1 槽位表：每段一首、各自自然收尾

从"三首长曲互相交叉淡化"改成"**每个槽位一首（开场 / 铺垫 / 低谷 / 高潮 / 片尾各 60–140 秒）**，
各自有自然收尾"。

**为什么**：长曲互切时接缝处两边都在收着，实测出现过 **−7~−8dB 掉电平**；
每段一首、段尾自然收束 + 段间交叉淡化，接缝才稳得住。

**怎么验证**：槽位表必须有"需要 / 曲子长 / 余量"三列，**余量全部为正**：

| 段 | 需要 | 曲子 | 余 |
|---|---|---|---|
| 开场·标题 | 20.0s | 32.0s | +12.0 |
| 第一章 | 51.7s | 53.6s | +1.9 |
| 第二章 | 86.6s | 87.2s | +0.6 |
| 第三章（低谷） | 40.0s | 42.2s | +2.2 |
| 第四章+片尾 | 109.5s | 109.4s | **−0.1**（靠 ≥3s 交叉淡化余量覆盖） |

槽位余量的实际作用：**重挑素材后段落只会变短 → 不需要重渲配乐**（省掉一次昂贵生成）。
反过来，**加镜头前先看槽位够不够**，不够就必须重生成或改槽位。

### 2.2 曲子比段落短：绝不能补零

**规则（伪码）**：

```
每段：s = 本段章节起点 − CROSS（首段为 0）
      e = 本段章节结束 + CROSS（末段为全片末尾）
      若 s + 曲子长 < e：e = s + 曲子长        # 收在曲子末尾
      若 e - s < 1.0：报错，不要静默
      offset = 曲子长 - (e - s)                 # 从曲尾倒着取
      若 i>0 且 s > 上一段结束 − MIN_OVL：s = 上一段结束 − MIN_OVL   # 提前本段起点（不是首段）
      MIN_OVL = 1.0s
```

**为什么**：曲子短于段落时，铺床函数会在末尾**补零**——成片里就出现一段**真空白**
（一段静音），听感比"接缝掉电平"糟得多。实测出现过某段缩短后比段落少 2 秒，
换段前留了真空。

**怎么验证**：把所有"曲长 − 段落长"列成余量表（§2.1），全为负就直接失败；
再对成片按 2s 滑窗 RMS 扫一遍，统计 **< −45dB 的近静音区段数，应为 0**。

### 2.3 段间电平：先逐段归一，再等功率交叉

**规则**：

```
每段先归一到统一 RMS（SEG_RMS ≈ 0.05 ≈ −26dBFS）  ← 再参与交叉
交叉淡化用 √（等功率），半宽 CROSS = 1.5s（总重叠 3.0s）
末端整体归一到 −18dBFS（再 ×0.95 留余量，并限幅防削波）
片头 1s 淡入、片尾 4s 淡出
```

**为什么**：
- **线性交叉在等幅处掉 3dB** → 必须等功率（√）。
- 各曲天然响度差很大（稀疏垫子比满编弦乐低 8dB 以上），不逐段归一会
  "**换段时突然深下去又冒上来**"。实测某道缝 **−8.2dB → +0.1dB**。
- 交叉长度扫过 0.5 / 0.8 / 1.5 / 2.5 / 4.0 秒：太短**掉 10dB**（两边都收着没人填），
  太长把开头的留白糊掉。**取 1.5，最深接缝 −3.3dB。**

**怎么验证**（逐交界点量三段 RMS）：

```
before = RMS[c−14, c−4]   mid = RMS[c−1.5, c+1.5]   after = RMS[c+4, c+14]
bump   = mid − max(before, after)          判据：bump < 1.5dB
```

同时**逐处看语义**：实测有一处 **−8.8dB** 落在"低谷章"，是两边都刻意收着造成的，
**保留**；判据只用来抓"不该出现的突起/凹陷"。
另一个坑：**插入了镜头就要把配乐交界点整体后移同样的秒数**，
否则音乐换段会跑到画面切换之前。

## 3. AI 生成配乐：风格串控制不住模型，必须手写 ABC

### 3.1 核心对照实验

| 控制方式 | 目标 | 实测 | 判定 |
|---|---|---|---|
| 只用 style 串写 "Eb major / I-V-IV-I / 49–61 notes per minute" | Eb 大调 · I–V–IV–I · 49–61 音/分 | **G 大调** ✗ · C–Em7–D · **124.2 音/分** ✗ | **三项全废** |
| **手写 ABC**（`K:Eb` + 和弦内联 + 音符数量自己数得清） | 同上 | **Eb:major** ✓ · **Eb-Bb-Ab-Eb** ✓ · **53.1 音/分** ✓ · 长音 0.317 | **三项全中** |

另一轮：style 串版本生成出 **G 大调 / 124 音/分**；同段换手写 ABC 后为
**Eb 大调 / Eb-Bb-Ab-Eb / 53.1 音/分**。

**结论：YuE2 走 ABC，不走提示词。** 提示词只能控"音色/氛围"这类不可量化的东西；
**调性、和弦、音符密度必须写进谱面。**

### 3.2 可复用 ABC 骨架

```
X:1
T:
M:4/4
L:1/32                       ← 一小节 32 单位，便于"数音"
Q:1/4=62                     ← BPM
V: Vocal clef=treble name="Vocal Melody" snm="Vocal"
V: Ins clef=treble name="Ins Melody" snm="Inst."
K:Gm                         ← 调性明写；Gm 下 B、E 自动降
V: Vocal
"Gm"z32|"Eb"z32|"F"z32|"Gm"z32|
V: Ins
G32|E16G16|F32|G16d16|
...（每 4 小节一组，Vocal/Ins 交替）
```

**调号陷阱**：`K:Gm` 下 B、E 已降；`K:Bb` 下同；`K:Eb` / `K:Cm` 下 B、E、A 都降。
所以音符**直接写音级字母**（`E` 就是 Eb），**不要再写临时记号**。
抬八度用**小写**（ABC 里小写 = 高八度），这是做"能量往上走"最省事的手段。

**密度怎么控**：给每种"形状"定每小节的音符排布（`L:1/32`，一小节恰好 32 单位）：

```
"open"   : 前段 pad 长音（0,16)+(1,16) → 后段 四×4（(0,8)(1,8)(2,8)(1,8)）
"sparse" : 几乎全小节一个 32 长音，偶尔半+半
"build"  : 从全长音 → 半+半 → 半+四+四 → 四×4，逐段加密
"low"    : 全小节 (0,32)，最空
"finale" : 前段空 → 中段半+半 → 后段加密 → 最后收在主和弦长音
```

**怎么验证**：写谱后**先自检再渲染**——调 `/v1/tools/abc/inspect`，
用返回的 `report.voices[*].sounding_notes` 求和、`nominal_duration_seconds` 算密度：

```
notes_per_min = total_notes / nominal_seconds * 60
```

这一步**不占显存**，能在渲染前就把密度打回重写。
上面的五段最终落到 **33.8 / 19.3 / 61.2 / 14.2 / 52.7 音/分**，全部落在配方区间内。

### 3.3 生成服务的调用契约（v0.2 形态）

`style` 串里**保留"音色/氛围"**，把"调性/和弦"删掉（反正控不住，写了反而骗自己）：

```
cinematic documentary score, warm strings, solo piano, sustained pads,
no drums, wide and spacious, leaves room for the picture, <NO_VOCAL>
```

| 接口 | 方法 | body / 参数 | 用途 |
|---|---|---|---|
| `/v1/plans` | POST | `{style, cot:"full"/"melody", seed}` | 只写谱（返回 ABC），不渲染 |
| `/v1/songs` | POST | `{style, abc, instrumental:true, seed, seconds?}` | 渲染 |
| `/v1/tools/abc/inspect` | POST | `{abc}` | 谱面自检（音符数/时长/BPM/是否合法） |
| `/v1/transcribe` | POST(multipart) | `{task:"full"}` + 音频 | 扒谱 |
| `/v1/jobs/{id}` | GET | — | 轮询任务状态 |
| `/v1/jobs/{id}/file/{name}` | GET | — | 下载 `native/audio.flac` / `score.abc` |
| `/v1/transcribe/{id}/file/{name}` | GET | — | 取扒谱产物（**不在 `/v1/jobs` 下**） |
| `/v1/admin/unload?transcriber=true` | POST | — | 卸载扒谱模型，释放显存 |

**三条硬经验**：

1. **不要用 `?wait=1` 跑长任务**：渲染 90 秒的曲子时，挂着的长连接会被中间的反向代理掐掉
   （`RemoteDisconnected`）。**改成异步提交 + 轮询 `/v1/jobs/{id}`**（3–6s 一次）。
   刚提交时 job 可能还没进注册表（404），**404 要重试而不是直接报错**。
2. **4xx 要把服务端返回的 `detail` 一起抛出来**——API 的错误体里有 usage 提示，
   是排查参数问题最有用的信息。
3. **渲染前先卸载扒谱模型**：扒谱工具会驻留数 GB 显存，和作曲模型抢同一张卡，
   渲染直接 `OutOfMemoryError`。顺序上"先扒谱 → 卸 → 再渲染"。

### 3.4 ABC 的两个语法坑（都踩过，报错信息照抄）

1. **每个声部每行最多 4 小节**。写成 8 小节一行会被 **422**：
   `group 1, Vocal: expected 1–4 measures after expanding Z rests`。
2. **两个声部必须交替成组**，不能"整条 Vocal 写完再写整条 Ins"：
   `group 1, Ins: expected V: Ins`。正确形态是
   `V: Vocal`(≤4 小节) → `V: Ins`(≤4 小节) → `V: Vocal` → …

### 3.5 长度要加"上限"

**规则**：请求里带 `seconds`（本段需要的时长 + 余量）。
**为什么**：模型自选长度可能远超谱面——实测一份名义 23 秒的谱渲染出了 **192 秒**的音频。
**怎么验证**：对每个槽位记录 `曲长 − 段落长` 的余量表（§2.1）；
余量为负或大得离谱（>2×）都说明长度没控住。

### 3.6 端到端跑一遍（runbook）

> §3.3 是契约、§3.1–§3.5 是判据，这一节是**照敲**：每一步**一条命令一行**，按
> "输入 / 期望输出 / 怎么判断成功"写。客户端就是本仓库自带的
> [`scripts/yue2_client.py`](../scripts/yue2_client.py)：只依赖 Python 3 标准库，
> **服务地址走环境变量**（`YUE2_BASE`，默认回环）、鉴权走 `YUE2_API_KEY`、超时 `YUE2_TIMEOUT`（默认 600s）。
> 下面的耗时/数值都是那次实测的量级，**换服务、换显卡要重新量**。

**第 0 步 · 地址与 key 进环境变量**

```bash
export YUE2_BASE=http://127.0.0.1:8100 YUE2_API_KEY=<key> ASR_URL=http://127.0.0.1:8083
```

- **输入**：你部署的作曲/扒谱服务地址、API key、一个 OpenAI 兼容的 ASR 地址。
- **期望输出**：没有输出（`export` 成功即可）。
- **怎么判断成功**：下一步能连上。别把 key 写进脚本文件，写进环境或配置文件。

**第 1 步 · 健康检查（兼冷启动探测）**

```bash
python scripts/yue2_client.py health
```

- **输入**：无（`/health` 免 key）。
- **期望输出**：`{"status":"ok", …, "pipe_loaded":false, "queue":0, "transcriber":"http://…:8101", "endpoints":[…]}`。
- **怎么判断成功**：`status=ok`。**首次调用要等 socket 激活（实测约 9s）**，所以客户端超时设 ≥600s；
  `pipe_loaded=false` 表示权重还没进显存——服务是**惰性加载**，空闲时显存为 0，第一次真干活才载入。

**第 2 步 · 先读服务自述文档**

```bash
python scripts/yue2_client.py doc
```

- **输入**：无（免 key；`GET /?lang=en` 是英文版，另有 `/openapi.json`、`/docs`）。
- **期望输出**：markdown 文档——快速开始、**生命周期与显存**、每个接口的字段表、故障排查表、已知限制。
- **怎么判断成功**：能看到 `endpoints` 与字段表。这是排错的地基：**任何接口报错都会带一个指向 `GET /`
  的 `usage` 字段**，`401`/`422` 的 `detail` 里也会写 `see GET / for usage / example payloads`——
  所以"**4xx 要把服务端返回的 `detail` 一起抛出来**"，别只抛状态码。
  `python scripts/yue2_client.py examples` 还能拿到**可以直接回发**的示例 body。

**第 3 步 · 让它先写一版谱（只写谱，不出音频、不占显存）**

```bash
python scripts/yue2_client.py plans --style style.txt --cot full
```

- **输入**：`style.txt` 一行风格串。**保留"音色/氛围"，把"调性/和弦"删掉**
  （反正控不住，写了反而骗自己），末尾拼上这段常量（**原文，一字不改**）：

  ```python
  NO_VOCAL = ("instrumental underscore only, absolutely no vocals, no choir, no voice, "
              "no humming, no spoken word, no vocal-like timbre, no vibrato pad, "
              "pure strings and piano")
  ```

  把它**固化成代码里的常量**、每次生成自动拼上（**不要手工拼**；为什么必须说这么死见 §4.2）。
- **期望输出**：job JSON（`status=done`、`bpm`、`note_counts`、`nominal_seconds`、`truncated.abc`）
  ＋ 落盘的 `score.abc`。
- **怎么判断成功**：拿到 ABC 文本就行。**但这一版只当草稿**：实测把要求写死反而更不听话（§3.1）。
  定稿走**手写 ABC**，五段槽位的输入长这样（段名按你的片子改）：

  | 槽位 | `K:` | `Q:1/4=` | 和弦 | 目标密度 | 形状 |
  |---|---|---|---|---|---|
  | 开场·标题 | `Gm` | 62 | i–VI–VII | 20–50 音/分 | 前段长音 → 后段四×4 |
  | 铺垫章 | `Bb` | 60 | I–vi–IV | **16–35** | 几乎整小节一个长音 |
  | 展开章 | `Eb` | 88 | I–V–vi–IV | 34–100 | 由疏到密逐段加密 |
  | 低谷章 | `Cm` | 58 | i–VI | ≈15 | 全小节一个 32 长音 |
  | 高潮+片尾 | `Eb` | 84 | I–V–IV–I | 49–61 | 末两小节收在主和弦长音 |

  §3.4 的两个语法坑在这一步就会咬人：**每个声部每行 ≤4 小节**、**两个声部必须交替成组**。

**第 4 步 · 渲染前先自检**

```bash
python scripts/yue2_client.py inspect --abc slot1.abc
```

- **输入**：手写（或第 3 步给的）ABC。
- **期望输出**：`report` 里 `voices[*].sounding_notes`、`nominal_duration_seconds`、`bpm`、`status`。
- **怎么判断成功**：`total_notes / nominal_seconds * 60` 落在该槽位的目标区间（§3.2 的算式）。
  实测五段落到 **33.8 / 19.3 / 61.2 / 14.2 / 52.7 音/分**，全部达标。
  **这一步不占显存**——密度不对就回去改谱，**不要拿渲染去试错**。

**第 5 步 · 渲染前先卸载扒谱模型（最容易漏的一条）**

```bash
python scripts/yue2_client.py unload --transcriber
```

- **输入**：无。
- **期望输出**：`{"status":"…"}` 之类的卸载回执。
- **怎么判断成功**：**不报错就行**。为什么必须做：扒谱跑完会把模型驻留 **约 3.4–3.5GB** 显存，
  和作曲模型抢同一张 16GB 卡，渲染直接
  `OutOfMemoryError: CUDA out of memory. Tried to allocate 722.00 MiB …`。
  顺序永远是"**先扒谱 → 卸 → 再渲染**"。

**第 6 步 · 提交渲染（异步，别加 `--sync`）**

```bash
python scripts/yue2_client.py songs --style style.txt --abc slot1.abc --seconds 90
```

- **输入**：风格串（末尾带 `NO_VOCAL`）、第 4 步自检过的 ABC、`--seconds`（本段需要 + 交叉淡化余量）。
- **期望输出**：`202` + job 对象，或（客户端默认行为）轮询到 `status=done` / `done_truncated`。
- **怎么判断成功**：状态是 `done` 或 `done_truncated`——**`done_truncated` = 撞了 `seconds`/`max_tokens`
  上限，不是故障**。三条要点：
  1. **不要用 `--sync`（`?wait=1`）跑长任务**：挂着的长连接会被中间的反向代理掐掉，报
     `http.client.RemoteDisconnected`。上面这条命令默认就是"异步提交 + 轮询"。
  2. **`seconds` 只是上限，谱面长度才是主控**（见 §3.5）：实测 `25` 语义 token ≈ 1 秒
     （`seconds=45 → 45.00s`、`max_tokens=1500 → 60.00s`），撞上限会**切在乐句中间**。
     经验做法：**想要 60 秒就写 `seconds: 90`**，让它自然收尾，再在时间线上裁。
  3. 期望耗时：32–110 秒的曲子，`elapsed_s` 实测 **19.8 / 32.4 / 50.3 / 43.5 / 63.2s**；
     140–170 秒的曲子 **85.5–120.6s**。**首次渲染还要多等权重惰性加载的 30–40s**。

**第 7 步 · 等它跑完（3–6s 查一次，404 要重试）**

```bash
python scripts/yue2_client.py jobs <job_id> --interval 6
```

- **输入**：第 6 步的 `job_id`。**轮询用 `/v1/jobs/{id}`，不是 `/v1/songs/{id}`**。
- **期望输出**：`{"status":"queued|running|done|done_truncated|failed", "audio_seconds":…, "elapsed_s":…}`。
- **怎么判断成功**：`done` / `done_truncated`。**刚提交时 job 可能还没进注册表 → 404，
  要重试而不是报错**（客户端重试 20 次再放弃）。服务是**单卡单 worker、串行**执行的，长曲会排队
  （看 `/health` 的 `queue`）；多段一起提交时 `elapsed_s` 含排队时间。
  另外：**别把渲染放进受限的后台 cgroup**（内存小、且约 3 分钟会被 SIGTERM），用前台跑、超时 ≥600s。

**第 8 步 · 下载成品**

```bash
python scripts/yue2_client.py get <job_id> native/audio.flac --out work/slot1.flac
```

- **输入**：`job_id` + 产物名。先 `python scripts/yue2_client.py files <job_id>` 可以列出全部产物
  （`native/audio.flac`、`audio.mp3`、`score.abc`、`request.json`、`result.json`…）。
- **期望输出**：`-> work/slot1.flac`。
- **怎么判断成功**：文件在，且 `ffprobe` 读出的时长 ≥ 本段需要 + 交叉淡化余量（§2.1 的余量表全为正）。
  顺手比一下 `score.abc`（渲染实际用的谱）和第 4 步的 `slot1.abc` 是否一致。
  小坑：**只有 `.flac` 没有 `.mp3`，通常是服务端找不到 `ffmpeg`**。

**第 9 步 · 转一份 128k mp3 给验证用**

```bash
ffmpeg -v error -y -i work/slot1.flac -b:a 128k work/slot1.mp3
```

- **输入**：第 8 步的 flac。
- **期望输出**：一个几 MB 的 mp3。
- **怎么判断成功**：能解出时长。**ASR 与扒谱都上传这一份**，别传母版大小。
  上传音频的表单字段名**必须是 `file`**，否则服务回 `multipart body needs a 'file' field`。

**第 10 步 · 纯器乐证据 A：ASR 转写（要空）**

```bash
curl -s -F file=@work/slot1.mp3 -F model=whisper-1 "$ASR_URL/v1/audio/transcriptions"
```

- **输入**：`ASR_URL` 指向一个 OpenAI 兼容的转写服务。
- **期望输出**：`{"text":""}`（或只有碎词）。
- **怎么判断成功**：**转不出连贯句子**。实测出问题的那一段，ASR 从纯器乐里**转出了一整句英文**——
  这是"里面混了语音类内容"的第一条独立证据；**只是碎词多半是幻觉，不要判死**。

**第 11 步 · 纯器乐证据 B：3–6Hz 调制（音节速率，要个位数）**

```bash
python -c "import numpy as np,subprocess,sys;SR=16000;p=sys.argv[1];x=np.frombuffer(subprocess.run(['ffmpeg','-v','error','-i',p,'-ac','1','-ar','16000','-f','f32le','-'],capture_output=True).stdout,dtype='<f4').astype(float)[:60*SR];f=np.fft.rfftfreq(len(x),1/SR);Y=np.fft.rfft(x);Y[(f<300)|(f>3400)]=0;y=np.fft.irfft(Y,len(x));w,hop=int(.025*SR),int(.010*SR);e=np.array([np.sqrt((y[i:i+w]**2).mean()+1e-12) for i in range(0,len(y)-w,hop)]);e-=e.mean();E=np.abs(np.fft.rfft(e*np.hanning(len(e))))**2;fe=np.fft.rfftfreq(len(e),hop/SR);print(round(float(E[(fe>=3)&(fe<=6)].sum()/(E.sum()+1e-20)*100),2))" work/slot1.mp3
```

- **输入**：第 9 步的 mp3（算法逐行解释见 §4.1）。
- **期望输出**：一个百分数。实测各段 **0.57%–5.91%**，修前那个离群段是 **16.19%**。
- **怎么判断成功**：**两条证据同时命中才定案**。用"**离群 + 第二条独立证据**"而不是绝对阈值：
  实测有一条**不是**人声的对照曲也到了 **9.85%** —— 没有干净阈值，别只盯数字。

**第 12 步 · 把成品丢回扒谱（回读对标，顺带拿 lab）**

```bash
python scripts/yue2_client.py transcribe --audio work/slot1.mp3 --task full --interval 6
```

- **输入**：成品 mp3（`task=full` = 调性 + 和弦 + 旋律 + 曲式；`--max-seconds 90` 可只转前 90 秒）。
- **期望输出**：job JSON，含 `status`、`melody_notes`、`vocal_notes`、`abc_measures`、`files` 表。
- **怎么判断成功**：`done`；**`vocal_notes` 应为 0 或极小**（第三条旁证）。
  注意：**这一步会把扒谱模型重新拉进显存**，所以下一个槽位渲染前要再回第 5 步卸一次。

**第 13 步 · 取回 lab，算密度 / 长音比例**

```bash
python scripts/yue2_client.py get <transcribe_job_id> melody_instrumental.lab --via transcribe --out work/mel.lab
```

- **输入**：第 12 步的 `job_id`。**扒谱产物走 `/v1/transcribe/{id}/file/{name}`，不在 `/v1/jobs` 下**，
  所以必须带 `--via transcribe`（不带会 404）。要调性/和弦就把 `key.lab`、`chord.lab` 各取一次。
- **期望输出**：`key.lab` 末字段是调性（如 `G:minor`）；`chord.lab` 第 1 行常是表头，取前 8 行第 3 列
  即和弦序列；`melody_instrumental.lab` 每行是"起 止"。
- **怎么判断成功**：`音符数 / 全长秒 × 60` 落回槽位目标（§1.2 口径）；**长音比例**（≥1.0s 的音符占比）
  垫底类应该高；峰值位置要按**成片里的使用窗口**重算（§1.1），不是按整首曲子。实测五段回读的
  调性与密度 **33.8 / 19.3 / 61.2 / 14.2 / 52.7 音/分** 全部落位。

**第 14 步 · 不合格时的修法（三类，都是"改输入重渲"，不是调音量）**

```bash
python scripts/yue2_client.py songs --style style.txt --abc slot1_fix.abc --seconds 90 --seed 4242
```

- **密度 / 调性不对** → 改 **ABC**（改 `K:`、改每小节的音符排布）。别指望 `style`：实测把
  "sparse / 每两秒一个音"写满，密度也只从 124 压到 **47.6 音/分**，仍高于垫底的 16–35。
- **有人声垫子** → 把 §4.2 那段 `NO_VOCAL` 原文**一字不改**拼到风格串末尾重渲
  （**同一个 seed 就够**：实测 16.19% → 0.93%、ASR 变空）；还不行再**换 seed 逐个试**。
- **长度不对** → 加 `seconds`（它只是上限，见 §3.5）或改谱面小节数。
- 每次重渲前都要回第 5 步 `unload --transcriber`（第 12 步刚把扒谱模型拉回来过）。

**第 15 步 · 收尾：把显存放掉**

```bash
python scripts/yue2_client.py unload --transcriber
```

- **输入**：无。
- **期望输出**：卸载回执。
- **怎么判断成功**：再跑一次 `health`，作曲侧 `pipe_loaded` 回到 `false`
  （扒谱侧的对应字段是 `model_loaded`）；空闲时两个模型的显存都应该是 0。
  不手动卸也行——服务是 **socket 激活 + 空闲自动退出**（实测空闲 300s 自杀，下次请求自动拉起），
  但**下一次渲染前**先卸一次更稳。

> **这个 runbook 里最容易做错的五件事**
>
> | # | 做错的写法 | 后果 | 正确写法 |
> |---|---|---|---|
> | 1 | `?wait=1` 跑渲染 | 长连接被代理掐掉 → `RemoteDisconnected` | 异步提交 + 轮询 `/v1/jobs/{id}`（3–6s，404 重试） |
> | 2 | 扒谱完直接渲染 | 扒谱驻留 3.4–3.5GB 抢卡 → `OutOfMemoryError` | 渲染前 `POST /v1/admin/unload?transcriber=true` |
> | 3 | 只抛状态码 | 丢掉 `detail` 里的 usage / 示例 body，参数问题查不动 | 把服务端 body 一起抛 |
> | 4 | 靠 `seconds` 定长度 | 谱面写多长就渲多长（名义 23s 的谱出过 192s 音频） | 谱面控长度、`seconds` 只当上限（§3.5） |
> | 5 | 按"点一下就有"估时间 | 冷启动约 9s、首次生成权重加载 30–40s、空闲 300s 自停 | 客户端超时 ≥600s，长任务前台跑 |

## 4. 纯器乐：两条独立证据 + 修法

### 4.1 判据

| 证据 | 原理 | 判定 |
|---|---|---|
| **ASR 转写** | 纯器乐不该转出**连贯句子**；只是碎词多半是幻觉 | 出完整句子 = 有语音类内容 |
| **3–6Hz 调制强度** | 这是**音节速率**；人声/念白在这一带有明显调幅，弦乐垫的起伏慢得多 | 取该带能量占总能量百分比 |

**怎么算 3–6Hz 调制**（可复现）：

```
1. 单声道 16kHz 解码，截前 60s
2. FFT 带通 300–3400Hz（人声频带）→ 逆变换
3. 25ms 窗 / 10ms 跳 算 RMS 包络 → 去均值
4. 对包络做 FFT，取 3–6Hz 的谱能量 / 总能量 × 100%
```

**两条同时命中才能定案**（单条可能是误判）。

### 4.2 实测分布与修法

| 段 | 3–6Hz 调制 | ASR |
|---|---|---|
| 开场 | 2.81% | 空 |
| **某铺垫段（修前）** | **16.19%** | **转出一整句英文** |
| **同一段（修后）** | **0.93%** | **空** |
| 其余段 | 0.57%–5.91% | 空 |
| 旧长曲 A（对照） | 9.85% | 空 |
| 旧长曲 B（对照） | 2.39% | 空 |

**定案逻辑**：16% 是其余段的 **3–27 倍**，又是唯一被 ASR 转出连贯句子的 → 判它的音色里
混进了**类人声的垫子**（颤音 pad / 类合唱音色）。**"离群 + 第二条独立证据"**比绝对阈值可靠。

**修法（把话说死，不要只写 `no vocals`）**：

```
instrumental underscore only, absolutely no vocals, no choir, no voice, no humming,
no spoken word, no vocal-like timbre, no vibrato pad, pure strings and piano
```

**同一 seed 重渲** → 调制 **16.19% → 0.93%**、ASR 变空。
**这条常量应固化成代码里的 `NO_VOCAL`，所有生成都拼上**——以后不要手工拼。

### 4.3 交付前复验（含成片复验）

1. 逐段跑 ASR + 调制体检，**要求 ASR 全空、调制回到个位数**。
2. **成片复验**：在交付的成片上按配乐段各抽一段再跑一遍——
   实测某段调制升到 **8.26%**（因为混进了脚步/呼吸等**原声**），但 ASR 为空 →
   判定为"原声，不是人声垫子"。**所以成片复验要结合该段有没有留同期声一起看。**
3. 排查时顺手排除另一嫌疑：把"原声最清楚"的那段丢给 ASR，返回空 → 同期声里没人说话。
