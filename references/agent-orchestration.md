# 多 agent 协作：什么时候派、怎么分工、怎么复核、怎么不丢工作

> **结论先行（两条）**：
>
> 1. **用 team 的第一动机不是"并行加速"，而是"主会话的上下文已经耗尽"。**
>    用户原话：「这里特别提到要用 team，是因为这个对话太太太 tm 长了，我感觉一下读不完」——
>    这次 Lead 自己的会话记录约 **7.2 MB（几千轮 / 8690 行事件）**，已经没法回头通读了。
> 2. **决定成败的不是"agent 聪不聪明"，而是"产物放在哪里"。**
>    同一件活里，**落盘的那份永远赢**——返回值被 kill 就归零，写进文件/数据库的还在。

---

## 零、总判据：什么时候派 teammate

> 当"**需要复盘的东西**"（长 trace、大代码库、几十份产出、几百张图）
> **比 Lead 剩余上下文还大**时：
> **不要再往 Lead 里塞。派 fresh-context teammate 去读，只让它回传"提炼后的结论"。**

Lead 上下文里应该留下的只有**结论 + 出处指针**，不是原始材料。

**任务描述必须自包含**（teammate 看不到 Lead 的历史）：

- 材料的**绝对路径**；
- **怎么打开/解开**（增量追加写的 `.zstd` 要先按魔数切帧再解，见 §四）；
- 产出文件的**绝对路径**与**字段结构**；
- **要回答的具体问题清单**（不是"看看这个 trace"）。

**还要给切片方法**（fresh teammate 读大材料也很慢，否则它一样会淹死）：

- 先 `grep` 关键词（报错串、素材号、`回滚`、`错误`），**只读命中处附近**，不要全文读；
  实测这条让一个 teammate 在有限上下文里读完了 **390 万字符**的材料；
- 按"轮次/阶段"切段，一次只处理一段并**立刻落盘小结**；
- 明确允许"读不完"：**把已核实的写成结论 + 标注未覆盖的部分**。

**额外一条实测技巧**：这类记录里**推理块的信息密度远高于文本块**——
文本块常被压缩成一句结论，推理块里有"我怀疑是 X → 做实验 → 实验排除 X → 实际是 Y"
的完整证据链。**重点是"怎么定位到原因"时，去看推理块。**

## 一、三种协作方式的实测对比

| 模式 | 产物放在哪 | 结果 |
|---|---|---|
| 批量 subagent（**11 个**并行审片） | **写进数据库**（带校验的唯一写入口） | ✅ 活：任何一个中途死掉，已写入的行还在，后续能查出来接着用 |
| 一次性 fan-out（**12 个**：6 选片 + 6 复核） | **只在脚本的返回值里** | ❌ 跑了约 **2 小时**、产出 **318 张联系表**、12 个里 11 个交出了完整结构化结论，**被 kill 的瞬间全部归零** |
| durable teammate（**3 个**） | **各自写一个 json** | ✅ 活：kill 掉某个 teammate，文件还在；可以中途追加要求 |

### 1.1 批量 subagent（写库）：量大、机械、彼此独立

**为什么成功**：产物不是返回值，是**数据库**。某个 agent 中途死掉，
已写进去的行还在；下一个 agent 还能查出来接着用。
**并发写同一张表必须有"带校验的唯一写入口"**（字段校验 + WAL + `busy_timeout`），
并且**给每条记录留作者标识**，出问题能追到人。
每个 agent 的写入批次要留档，**结论可追溯到"是谁写的"**。

**失败模式**：

- 拿不到中间过程，调度者只能看"库里多了几行"猜进度；
- **没有对抗**：每个 agent 各看各的格子，**没人复核别人写的摘要**——
  后来的证据字段偏差（见 §三）就是这么漏过去的；
- 并发写同一张表需要纪律，否则互相覆盖。

**适用**：量大、机械、彼此独立、产物天然能落库/落盘的活（逐条打标、逐文件审计、逐日入库）。

### 1.2 一次性 fan-out（返回值）：跑得动，收不了尾

实测时间线（同一天）：

```
00:24  第一次提交被解析器打回（脚本里用了尖括号占位符）
00:24  重提交成功 → 12 个子 agent 陆续启动（6 选片 + 6 对抗复核）
01:49  最后一个产出文件落盘
02:08  调度者轮询："总联系表数 = 318"
02:18  放弃并 kill，理由："agents 已停滞约 30 分钟无产出，改为自己基于已生成的产物定稿"
```

总时长约 **1 小时 54 分**，产出 **318 张联系表**，
**12 个子 agent 的逐帧观察全都在磁盘上**——但**聚合返回值一个字节都没回来**。

**四条失败模式（按严重度）**：

1. **单点长任务、没有中间可见性。** 编排层只回报"阶段"，
   调度者只能靠数产出文件个数猜进度。停滞 30 分钟，
   **从外部完全看不出是卡住还是在干活。**
2. **停滞 → kill → 聚合结果丢。** 结果只存在于脚本的返回值里；脚本被杀，返回值即消失。
   **这是本次最大的教训。**
3. **不能中途改需求。** 12 个 agent 的任务书在开始时冻结；
   而这批素材的判据在一小时后就被推翻了（见 §二的反面教训），它们无从知道。
4. **有 agent 死在半路。** 12 个里有 **1 个一次都没发出结构化结论**，
   而它最锋利的对抗结论**只存在于它的推理文本里** ——
   **任何"只收集结构化输出"的汇总方式都会把它整条丢掉。**

**适用**：可完全并行、**单轮**、结果**当场落盘**、不需要中途改需求的批量审计。
**反例就是这次**：需求会变、要人盯着、要能中断。

### 1.3 durable teammate：任务板 + 结论落盘 + 中途追加要求

3 个 teammate 的实测画像：

| teammate | 任务 | 步数 | 工具调用 | 读图 | 写文件 | 任务板操作 | 消息 |
|---|---|---|---|---|---|---|---|
| A 版 picker | 主推版素材 | 100 | 129 | 49 | 4 | 8 | 3 |
| B 版 picker | 备选版素材 | 108 | 137 | 29 | 8 | 2 | 4 |
| 专题 picker | 某一整类素材重挑 | **39** | 57 | 24 | 1 | 2 | 1 |

**逐条对应失败模式的补救**：

| fan-out 的失败 | teammate 的补救 |
|---|---|
| 结果只在返回值里 | **结论落盘成 json**；kill 掉某个 teammate，文件还在 |
| 没有中间可见性 | teammate 是**可寻址、可 resume** 的；看状态、直接发消息问 |
| 不能中途改需求 | 调度者中途发了 **4–5 轮追加要求**，在下一个 step 边界收到 |
| 一个 agent 死了就没了 | 任务在**共享任务板**上（带 revision / owner / 依赖），可重新认领 |

**追加要求的正确用法（这是它真正的价值）**：

1. **给预算 + 结构要求**（附反馈原话逐字）；
2. **实现了新能力后解锁旧约束**（"裁底已实现 → 把第三章补到 4 条"）；
3. **跨 agent 传结论时只传文件路径**，不把长文塞进消息；
4. **要求复核被否掉的条目**（附**具体命令**——给了命令的复检要求，执行率 100%）；
5. **自我更正**：同一轮内推翻自己 40 分钟前的判据
   （"我把手/杖入画当成缺陷了，**更正上一条**"）——
   **注意：推翻一个约束时，要同时说明另一个约束是否保留、为什么。**

**失败模式（也要说清楚）**：

- **调度者是单点。** 跨 agent 的信息全靠调度者手动转发；它上下文爆了，整队就瞎了。
- **一个文件只能有一个 writer。** 实测：一边发消息说"其它章节不用动"，
  一边**直接往对方的产物文件里塞了一个字段** → 对方读文件时才发现，
  只能自己判断"按消息还是按文件"。**指令走文件还是走消息，必须二选一。**
- **成本高。** 3 个 teammate 合计 **247 步 / 323 次工具调用 / 几小时墙钟**；
  而其中一个只用 **39 步**就交出了"整类素材重挑"的结论。**不是所有活都值得开 teammate。**
- **任务板本身不会叫醒人。** 某个任务完成了，别的 teammate **不会自动知道**，
  必须由调度者把结论**递**过去。

### 1.4 怎么选

| 场景 | 用哪个 |
|---|---|
| 机械批量、产物能落库、无需中途干预 | 批量 subagent（+ 带校验的写入口） |
| 同一批数据要 N 路并行、一轮出结果、结果当场写盘 | 一次性 fan-out（**但必须让每个 agent 自己写文件**，并且**不要中途 kill 它**） |
| 需求会在过程中变、要交叉验证、要能中断/续跑 | **durable teammate**（每个 writer 一个文件，调度者只转发结论路径） |
| 只是"帮我查个东西" | 直接自己做 |

## 二、任务描述怎么写才有效

### 2.1 有效的写法（每条都有实测代价作为依据）

1. **写死唯一的产物文件路径 + 明确的禁止项。**
   「你**只能写**这一个文件，不要碰其它文件，**不要跑渲染**。」
   → 多个 teammate 各写一个 json，**零写冲突**；
   反例是 12 个 agent 往同一个目录灌图片，回收时要人工点名。
2. **给数量 + 时长预算。**
   → **没有预算就收不住**：同一批素材，无预算时交出来的总长是
   **175.5s（超目标 25.5s）**；给了逐章预算后才收敛到 **146.5–149.2s**。
3. **硬要求 + 可验证的证据字段。**
   「**每条都要自己抽帧复核**，并在证据字段里写**只有看过帧才说得出的细节**」
   → 让"编造"变成可被证伪的事（§三就是这么抓出来的）。
4. **结构化 schema，且把字段语义写清楚。**
   实测：因为没定义"`accept` 是什么意思"，**4 个复核员都卡在"窗口对但可以更好"上**，
   烧掉大量推理 → 正确写法是「**只有你亲自看过、且同意这个窗口时才给 true**」。
5. **给"为什么"：决策者原话逐字 + 参考产物的路径。**
   这样 agent 能自己判断"这条原话适用于我手上哪条素材"，而不是机械照做。
6. **硬要求要配"怎么验"**（给出具体命令）。
7. **限制搜索面、禁止全文读**（见 §零）。
8. **规定汇报格式与长度上限**（"报告 5 行以内"），调度者才读得完。

### 2.2 反面教训

- **负向约束会反噬。** 「不要选仪表台/后视镜/手入画的车拍镜头」被三个 agent 严格执行，
  结果①把一整批素材几乎全禁掉，②后来决策者说"手入画是**优点**"，还要发更正。
  **负向约束要么写清"为什么"（"观众看不出在表达什么"），
  要么写成可判定的量（"底部黑带 > 20% 画幅"），别写死一个动作。**
- **指令走文件还是走消息，必须二选一**（见 §1.3）。
- **并行脚本里不要用 `<...>` 占位符** —— 第一次提交就是这么被 JS 解析器打回的。
- **长任务必须有"停滞判据"。** 这次是靠"30 分钟没有新产出文件"人工判定后 kill；
  更好的做法是**让每个 agent 每完成一个单元就写一行状态文件**，
  这样"停滞"是可见的、可自动判定的。
- **不要把"最终答案"定义成"最后一段文本"** —— 那通常是客套话（见 §四）。
- **一个 agent 一个交付物。** 让 12 个 agent 各写一个 json，回收就是 `glob("*.json")`；
  让 12 个 agent 往同一个目录灌图片，回收时要人工点名。

### 2.3 开多 agent 前的 checklist

- [ ] 每个 agent 的**产物路径唯一**，且是**文件**（不是返回值）；
- [ ] 输出 **schema 写死**在描述里，并附**字段语义**说明；
- [ ] 有**预算**（条数 / 时长 / 字节 / 步数上限）；
- [ ] 有**证据字段**，且说明"复核员会用放大帧验伪"；
- [ ] 有**停滞判据**与**可中断点**（agent 能随时把当前结论落盘）；
- [ ] 需求可能变 → 用 durable teammate；需求冻结 → 才用一次性 fan-out；
- [ ] 调度者只转发**结论的路径**，不转发长文；
- [ ] 收尾时**同时**收集"返回值 + 落盘文件 + 会话记录"三份，别只信一份。

## 三、独立复核：证据字段的"看过"不等于"看准"

**先给结论**：统计上证据字段是**真的**——12 个子 agent 合计 **306 次读图**
（有一个复核员一个就 66 次，把 10 条候选全部重看了一遍全分辨率帧）；
teammate 侧也有 49 / 29 / 24 次。**"看过"是可信的。**

**但"看过"不等于"看准"。** 复核员用 **1:1 放大帧**重看同一条素材时，
抓到四类**系统性**偏差：

| 类型 | 原写的 | 放大复核实测 |
|---|---|---|
| **事实错误** | "人物只在末帧边缘出现"／"无人物" | 整条 6.4s 全程都有人在径上，第 0.6s 就有背影，约占画面高 9–10% |
| **方位说反** | "**左侧**草甸上一个红衣小人沿湖走" | 红衣人在 **x≈86% 画幅**，在**右**侧 |
| **不完整 / 过度断言** | "画面里**没有任何人**" + "左侧岸边露出一小片坡地" | 左侧岸边有 2–3 个小人影，而且**漏了左侧的木屋** |
| **差一个量级** | "栈道中段一个背包人影，**只有画面高度约 1/12**" | 实测占画面高 **1/4 ~ 1/5**、在画面正中，是**中景队友的背影** |

第 4 类后果最重：如果采信原描述，会把一条"前面有人"的镜头当开场用。
复核员的判词是决定性的：「原文与实拍差了一个量级——**这是一票否决项**，本章开场必须换人。」

**复核也确认了大量证据字段是真的、经得起放大**：
"斜搭的木板（像小木凳）"✓、"几条长长树干影子斜切过苔藓地面"✓、
**逐字读出路边牌上的字并纠正了自动摘要**✓。
**复核还会修掉自己的过度怀疑**：用音频测量反证了"这批全是车内行驶"的说法
（某条均值 **−34 dB**，比车内镜头低 **24 dB**，与"步行栈道环境声"一致）。

**还有一条诚实性的正面证据**：某 agent 不确定时会**去补帧**而不是编——
自己写"约 3.1 秒画面顶部被一块失焦的棕肤色遮挡（**像**手/手指压到镜头）"，
随后自己加了一句：`"我不想在它是叶子的时候声称那是手指。"`

### 3.1 所以流程必须是三步

```
证据字段（选片员自证） → 独立复核员用 1:1 放大帧重看 → 才定窗口
```

**把证据字段当作"自动可信"的字段，就是这类错误能进交付的原因。**

### 3.2 复核真正的产出是什么

不是"我觉得这条好"，而是：

> 「**我抽帧看过，窗口是 X–Y，这里有一个手/一个人/一个电线杆，占画幅 Z%**」

——可被下一个人复核、可被写进 notes、可被渲染器消费。

**复核也抓过"窗口不成立"的典型**：一条被推荐为"最干净的一截"的窗口，
放大后发现**推荐的窗口内**右下角就有一只握机的手 + 手柄 + 袖子（约占右下 1/4）
→ 直接判不通过。

**还有一条正面形态值得学**：同一条素材被**三个 agent 独立看过**，
窗口一次比一次准（`4.0–10.5` → `4.0–12.5` → `4.5–11.5`）——
第二个 speaker **没有直接采纳**第一个的推荐，而是自己抽帧复核后放宽/收紧，
并写清"为什么放宽"（"2.8s 那辆车 4.2s 已出画"／"12.0s 之后右侧进标志牌结构"）。

## 四、中断恢复：把被 kill 的 fan-out 的结论捞回来

**场景**：一次性 fan-out 被 kill 之后聚合结果丢了，
但**每个子 agent 的会话记录还在磁盘上**。

**两步**：

```bash
node scripts/unzstd.js <in.zstd> <out.jsonl>     # 解压（按魔数切帧）
python scripts/sess_recover.py                   # 抽出助手文本/结构化结论
```

这次恢复了 **40 个子 agent 的记录**（含那 12 个的全部逐帧观察），
重挑阶段还直接拿它们当"上一轮的观察记录"用。

### 4.1 坑 1：一个压缩文件里有**多个帧**

这类日志是**增量追加**写的：一个 `.zstd` 里是**多个 zstd 帧首尾相接**，
而很多解压库（例如 Node 的 `zlib.zstdDecompressSync`）**只解第一帧、并且不报错**——
直接解只能拿到 **300 字节左右**的文件头。

**修法**：按 zstd 魔数 `0x28 B5 2F FD` 切帧、逐帧解再拼：

```js
const MAGIC = Buffer.from([0x28, 0xb5, 0x2f, 0xfd]);
// 扫描所有魔数位置 → 依次 subarray 切段 → zstdDecompressSync 每段 → Buffer.concat
// 逐帧 try/catch 计数 ok / bad（坏帧跳过不致命）
```

**第一版抢救脚本的失败现场**：它"把每个会话的最后一段助手文本写成文件"，
跑完的结果是**每个会话"行=1"、产物全是 0 字节**。
⇒ **抢救脚本必须打印每个会话的帧数 / 字节数 / 行数**，
"行=1"这种异常一眼就能看出"解压只解了第一帧"。
（修好后同一个文件解出 **353 / 371 / 139 帧全部 ok**。）

### 4.2 坑 2：抓错了记录类型

"最后一段助手文本"通常只是「都检查完了，这是我的独立复核」这种**收尾句**。
真正的结论在**结构化交付**里：`type == "tool/call"` 且
`data.name == "<结构化输出工具>"` → `data.arguments` 就是完整 JSON。
而**中间判断在推理文本里**。

⇒ **只收集结构化输出，会静默丢掉"没发出结构化结论的那些 agent"的全部工作量**
（实测：12 个里有 1 个就是这种情况）。

### 4.3 顺手纠正一个计数方法

任务清单里写"54 个产物文件"，实际是 **40 个有内容** + **14 个 0 字节的空壳**
（第一版脚本失败留下的）。**看文件个数会误判工作量——要看索引文件的行数。**

### 4.4 教训（这一节最值钱的三条）

1. **让 agent 把结论写文件，返回值只当信号。**
   同一批活里三种产物的存活率：写库（活）、结构化返回值（被 kill 后丢）、写 json（活）。
   **落盘的那份永远赢。**
2. **会话记录是最后一道兜底，但要知道它的形状**：
   多帧压缩要切帧；结论在工具调用的参数里；中间判断在推理块里。
3. **别把"最终答案"定义成"最后一段文本"。**

## 五、一次真实的分阶段节奏

```
1. 入库 + 抽帧 + 拼联系表                     （单 agent / 脚本）
2. N 个 subagent 并行审片 → 写库               （唯一写入口 + 批次留档）
3. 调度者汇总 → 第一版分镜 → 粗剪              （脚本）
4. 反馈 → 缩小到"这一章重挑"
   ├─ 列当天素材 → 拼联系表
   ├─ 人眼/读图复核 → 写证据字段
   └─ 改分镜 → 重建 → 清缓存 → 重渲 → 量化 QC
5. 反馈变多 → 拆成多个 durable teammate 并行
   ├─ 两个版本各一个 picker
   ├─ 一个专题 picker（把某一整类素材全部逐帧看完 → 给共性结论）
   └─ 一个独立复核员（用放大帧验伪别人的证据字段）
6. 调度者收敛 → 定稿 → 打包 → 文案
```

**调度者的职责**：划清写入范围、给每个任务写清验收标准、
把"选片 json"变成"分镜表"、**在最后跑一遍验收**。
**调度者不应该自己也去做选片**——那会和 teammate 冲突；
它也不应该把长文在 agent 之间转发（只转**结论的路径**）。
